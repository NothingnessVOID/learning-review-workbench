# 备份、恢复与升级

设置与备份 → 生成备份。业务服务串行排队并通过 SQLite backup API 建立一致性快照，复制该快照引用的全部来源，生成 SHA-256/字节数清单和对象数量。备份保存在数据目录 backups/，也可下载 ZIP。凭据不包含在包中。

恢复流程：选择 ZIP → 校验并预览数量 → 输入“恢复此备份” → 本地确认。候选数据库先在 staging 临时目录打开，检查 user_version、integrity_check、精确结构（拒绝额外触发器等）、来源哈希、对象数量、主要引用。校验失败不切换当前库。

确认时先备份当前库，再关闭连接并切换；失败尝试恢复原库。旧来源哈希文件保留，个人记录授权清空为默认权限。恢复前备份可从数据目录 backups/ 找回；不要向外部 Agent 暴露全库恢复能力。

备份含私人数据，未加密，不自动上传。读取迁移用的导出 ZIP 不是备份，不能拿来全库恢复。分享模式只按指定词脱敏，不保证自动识别所有身份或财务内容。

升级：先备份 → 安全停止服务 → 更新源码并 npm ci/npm run build → 启动 → 检查资料。真实数据库与源码目录分离，重装依赖不删数据。本版 schema=1 尚无跨版本迁移；不匹配的备份会拒绝，不尝试猜测迁移。

实际恢复测试：tests/domain.test.ts 在隔离临时数据目录创建快照、增写一条记录、验证预览无写入、执行恢复，并确认恢复的是选中快照；tests/security.test.ts 篡改来源哈希被拒。完整输出见 TEST_REPORT.md。

## 1.1 可靠性修订

素材导入与备份采用独立上限。完整备份最多 10,000 个 ZIP 条目、128 MiB 展开数据、64 MiB 压缩包；生成和恢复校验同一边界，压缩包 base64 载荷也适配本地 HTTP 上限。超过上限会明确拒绝生成，不会给出不可恢复的成功文件。大规模数据继续保留原始文件的独立副本。

当前来源文件丢失或哈希错误时，恢复会先保留带缺失／损坏清单的抢救副本，再安装已验证备份。抢救副本明确标为不完整，不能冒充有效历史备份。恢复前再次验证暂存字节；数据库、来源或上下文替换失败时回滚，失败步骤有错误说明。正常数据库损坏到无法打开的灾难恢复，仍需先保留整个目录，由维护者处理。

备份可勾选包含运行上下文，默认关闭。选中时保存固定语境和提示模板的当前修订及来源摘要，恢复到新目录后可继续使用；本地更早的上下文历史不包含在该选项内。凭据不入备份，恢复后个人记录 MCP 授权会清空。备份若不含上下文，恢复目标现有上下文保持不变。

本轮没有提升 SQLite schema version。旧版备份仍可预览与恢复；导入预览中的旧大载荷会在新服务清理时移除，已经提交的幂等摘要保留，未提交且过期的预览需要重新选择文件。正式来源、笔记和待审草稿保留。

恢复包含上下文的备份时，被替换的整套上下文及其历史会留在数据目录 `runtime-context-history/`，便于回找；它们不会混入当前 Agent 上下文，也不会被普通备份选项递归打包。
